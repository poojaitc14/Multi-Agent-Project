# E-commerce Returns, Refunds & Fraud Triage — Multi-Agent Project Plan

## Context

This is a training/final-project build of a multi-agent system for e-commerce return/refund fraud triage. The project folder (`Multi-Agent-Project`) currently contains only a git repo and a placeholder README — this plan is being built from scratch via a requirements interview, one question at a time, with no assumptions made. Nothing is being built yet; this document is the running record of decisions.

## Problem Statement (as given)

Given a customer's return/refund request with photos of the item, assess whether the photo evidence is consistent with the claim, score the request for fraud risk, and decide approve/deny/escalate — with a policy check that neither the vision agent nor the fraud model gets to bypass.

**Agents:**
- Orchestrator (light): classifies the request, maintains per-customer conversation state across sessions, invokes the two doer agents, applies the Decision Agent's verdict
- Image Parsing Agent: analyzes uploaded photos, checks consistency with customer's description
- ML Fraud Scoring Agent: scores using order history, account age, claim frequency, address-mismatch signals
- Decision Agent: combines image assessment + fraud score against written refund policy, issues approve/deny/escalate-to-human

**MCP integration:** MCP server wrapping order-management system (`get_order`, `issue_refund`) — `issue_refund` only fires on Decision Agent "approve", never directly from fraud/image agent.

**DB architecture:** RDS/Postgres (orders, refund transactions) · DynamoDB (per-customer conversation state, rolling claim-frequency counter) · S3 (item photos, chat transcripts).

**Stateful design:** Conversation state persists per customer across sessions. Fraud agent keeps sliding-window claim counter per customer/address.

**Communication:** Orchestrator calls Image + Fraud agents as parallel tool-calls, then hands both outputs to Decision Agent synchronously — no async pub/sub needed.

**APIs:** DummyJSON / FakeStoreAPI (order/product data), free package-tracking API (e.g. TrackingMore free tier) for shipment status feeding fraud signal.

## Agent Work Breakdown & Model Recommendation (for Q6 final split) — RESOLVED, see final assignment below

### Orchestrator (light)
- Classifies incoming customer message (new claim vs. follow-up vs. general inquiry)
- Reads/writes per-customer conversation state (DynamoDB) so multi-day conversations resume
- Extracts/validates order ID, calls `get_order` (via MCP)
- Invokes Image Parsing Agent + ML Fraud Scoring Agent as parallel tool-calls
- Hands both outputs to Decision Agent synchronously
- Applies Decision Agent's verdict: calls `issue_refund` (via MCP) only on "approve"; otherwise composes a denial/escalation response
- **Work profile:** classification, dialogue/state management, tool orchestration, structured I/O. Highest call volume (every turn) — favors a fast, cheap, reliable-tool-calling model over a maximum-reasoning one. No vision needed.
- **Recommended model:** **Qwen 3 (e.g. 7B–14B via Ollama)** — benchmark leader for general reasoning + tool/function calling among open models, Apache 2.0, efficient enough at smaller sizes for low-latency per-turn use.
- **Final model (Q52, supersedes the Qwen 3 recommendation above and the "Final model assignment" below):** **GPT-4.1 mini (hosted).** Trades the $0-per-call local model for faster, more reliable tool-calling — a deliberate tradeoff given this is the highest-call-volume agent (every conversational turn), so its hosted cost accumulates faster than any other agent's.

### Image Parsing Agent
- Analyzes uploaded photo(s) of the returned/damaged item
- Judges whether the photo is consistent with the customer's stated claim (e.g. "screen cracked," "wrong item," "missing parts")
- May need to cross-check the photographed product against the actual ordered product (catches reused/stock photos or wrong-item claims)
- Outputs a structured consistency assessment + reasoning for the Decision Agent
- **Work profile:** pure vision judgment; this is the core fraud-relevant signal (staged damage, mismatched item, reused photos) and its output materially affects a decision that can trigger real money movement (`issue_refund`) — accuracy matters most here.
- **Final model (superseding the GPT-5.6 Sol recommendation below — GPT-5.6 is not available to this user, see "Vision Model Comparison — Revised"):** **GPT-4.1 mini and Llama 3.2 Vision 11B, both supported with a model-selector in the Streamlit UI.**

### ML Fraud Scoring Agent
- Scores fraud risk from: order history, account age, claim frequency (DynamoDB sliding-window counter), address-mismatch (tracking API vs. claimed delivery address)
- Numerical/pattern-based reasoning over structured signals fetched via MCP tools, not open-ended generation or vision
- **Work profile:** needs strong numerical/logical/pattern reasoning and reliable multi-tool-calling (fetch several signals, then score), not general world knowledge or vision.
- **Recommended model:** **DeepSeek (V4/R1 or a smaller distilled variant) via Ollama** — standout for math/step-by-step reasoning, ranks #1 open-weight on agentic/tool-calling benchmarks per 2026 sources.
- **Final model (Q52, supersedes the DeepSeek recommendation above and the "Final model assignment" below):** **GPT-4.1 mini (hosted).** This agent's actual judgment comes from the trained ML model (Q7) — the LLM's job is mechanical (call tools, explain a score) and runs once per claim, not every turn, so a hosted model's reliability on structured output was judged worth the modest added cost.

### Decision Agent
- Combines the Image Parsing output + Fraud score against the written refund policy
- Issues the final approve/deny/escalate-to-human verdict — the **only** thing allowed to trigger `issue_refund`
- **Work profile:** the highest-stakes step in the whole system — must correctly interpret policy text (thresholds, exceptions), weigh two heterogeneous upstream signals, and can never be bypassed. Needs the most trustworthy reasoning available among the chosen models, since real money moves on its verdict.
- **Recommended model:** **DeepSeek (same family as Fraud agent, or a larger variant if hardware allows)** — strongest available local/open reasoning per research, appropriate given this agent is the final, non-bypassable gate.

## Tool List Per Agent (derived from problem statement + decisions so far)

**PII boundary (see Q27 / "Data privacy / PII boundary" below):** every tool an agent's LLM can see returns a `customer_ref`/`order_ref` opaque token plus de-identified or derived fields — never a raw name, email, phone, address, or payment detail. Descriptions below reflect that.

**Binary payloads are base64 (confirmed by Slice 1 implementation):** MCP's JSON-RPC transport can't carry raw `bytes` — a real `store_photo` call with actual bytes fails serialization. Every tool that moves a photo (`store_photo`, `get_photo`, and later `redact_photo`/`analyze_image`) takes/returns a base64-encoded string, not raw bytes. This was discovered building the Orchestrator MCP server, not decided in advance — noted here so the Image Parsing server (not yet built) follows the same convention.

**Orchestrator**
- `get_order(order_ref)` — product, amount, order_date, delivery_status, category tied to the claim (order-management) — no shipping name/address/payment fields
- `issue_refund(order_ref, amount, reason)` — write tool; **only** called after Decision Agent returns "approve"; resolves the real payment method internally (order-management) — the LLM supplies only the ref, amount, and reason. **Idempotent (Q32):** keyed on `order_ref`+`claim_ref` — a duplicate call (retry, re-run) returns the existing refund transaction instead of writing a second one
- `get_conversation_state` / `put_conversation_state` — per-customer session state, read/write, keyed by `customer_ref` (DynamoDB)
- `store_photo(claim_ref, photo_base64)` / `get_photo(claim_ref) -> photo_base64` — uploaded item photos, keyed by `claim_ref`, base64-encoded over the wire (S3)
- `store_transcript` — chat transcript archive, keyed by `customer_ref` (S3)
- invokes Image Parsing Agent + ML Fraud Scoring Agent (parallel), then Decision Agent (sync) — agent-to-agent calls, not MCP tools themselves
- resolves the customer's real ID/email (Q15) to a `customer_ref` at intake — this resolution is application code, not an LLM call, and the raw identifier is never placed in any agent's prompt context

**Image Parsing Agent**
- `get_photo(claim_ref)` — retrieve the claim's uploaded photo(s), already redacted (S3)
- `get_product_reference` — pull the ordered product's reference image/description to cross-check against the photo (order-management / product API)
- `redact_photo` — auto-detects and blurs incidental text/faces (e.g. a shipping label) in a photo; runs before the photo is handed to **either** vision model
- `analyze_image` — the vision judgment itself, always called on the redacted photo (open design question below)

**ML Fraud Scoring Agent**
- `get_order(order_ref)` — order history, de-identified (order-management)
- `get_account_info(customer_ref)` — **revised by Q59:** `account_age_days`, `total_orders_lifetime`, `total_returns_lifetime`, `customer_support_contacts_90d`, `previous_dispute_count`, `address_match` — no name/email/phone. Superseded the original `prior_claim_count` field once it became clear the actual trained model (Slice 2/4) needs this specific set of columns instead.
- `get_claim_frequency` — read the sliding-window claim counter per `customer_ref` (DynamoDB)
- `increment_claim_frequency` — record this claim in the counter (DynamoDB, write)
- `get_tracking_status(order_ref)` — **revised by Q59:** `delivery_status` only (TrackingMore API). `address_match` moved to `get_account_info` above — see Q59.
- `score_fraud_risk` — call the trained ML model with engineered features, return a risk score **and its top contributing features (Q34)** — see "ML Fraud Scoring model" below

**Decision Agent**
- `search_refund_policy(query)` — **RAG lookup (Q50, vector store revised by Q54), fully supersedes `get_refund_policy`/Q40 (confirmed Q56, no full-text tool kept).** Embeds the query via OpenAI `text-embedding-3-small` and retrieves the **top-5 (Q56)** relevant chunks — **chunked by clause/category, not fixed-size (Q56)** — of `docs/refund_policy.md` from **OpenSearch Serverless**, plus each chunk's `policy_version`, rather than fetching and loading the entire document into context. **Not token-gated (Q56)** — read-only, no PII, no money moved. No confident match → the Decision Agent escalates rather than guessing (Q56).
- No write tools, and never calls `issue_refund` directly — returns a verdict object to the Orchestrator, which is the only one that acts on it

**Resolved (Q41):** `analyze_image` is confirmed as a formal MCP tool call on the Image Parsing MCP server — not a bare underlying model call — consistent with the "every tool call must go through MCP" rubric requirement and everything already built around it.

**Security note carried into MCP server grouping decision:** the `issue_refund` write path should ideally be isolated (credentials/access scoped) so only the Orchestrator's MCP client can reach it — Image/Fraud/Decision agents' MCP clients should have no access to that capability at all, enforcing the "policy check neither vision nor fraud model can bypass" requirement at the infrastructure level, not just in application logic.

### Structured agent outputs

Per Q28, each agent's output is a typed object, not free text, enforced by three stacked layers rather than one:

1. **Constrained decoding at the model** — Ollama's `format=` schema parameter for the remaining local models (DeepSeek-R1-Distill for Decision Agent, local Llama 3.2 Vision for Image Parsing); OpenAI's JSON-schema `response_format` for GPT-4.1 mini (Image Parsing's hosted option, and — since Q52 — Orchestrator and ML Fraud Scoring too). Invalid tokens are excluded during generation, not caught after the fact.
2. **`output_pydantic` on every CrewAI Task** — CrewAI validates the raw response against the schema and re-prompts on mismatch, as a check independent of whatever Layer 1 already enforced.
3. **A `guardrail` function per Task** — catches business-rule violations a schema can't express on its own, e.g. the &gt;$200 always-escalate rule (Q21): a decision of "approve" with a refund amount over $200 fails the guardrail and triggers an automatic corrective re-try.

The four schemas:

| Agent | Output shape |
|---|---|
| Orchestrator | `ClassificationResult { request_type: new_claim \| follow_up \| general_inquiry, order_ref }` |
| Image Parsing | `ConsistencyAssessment { verdict: consistent \| partially_consistent \| inconsistent \| no_photo, product_match: bool, reasoning }` |
| ML Fraud Scoring | `FraudAssessment { risk_band: low \| medium \| high, risk_score, key_signals, reasoning }` |
| Decision | `Verdict { decision: approve \| deny \| escalate, refund_amount, refund_form, policy_clause, policy_version, reasoning }` |

Since the Decision Agent runs a smaller local 8B model that follows format instructions less reliably than GPT-4.1 mini, its agent backstory additionally includes 2–3 few-shot input→output examples to anchor the shape further. **Superseded by Q52:** this originally applied to Orchestrator and Fraud as well, back when all three ran locally — now that both have moved to GPT-4.1 mini, only Decision still needs the crutch.

**`key_signals` grounding (Q34):** `score_fraud_risk` returns its top contributing features per call (SHAP-based), and a Layer-3 guardrail on the Fraud Task checks every entry in `FraudAssessment.key_signals` against the fixed vocabulary of real model features — CrewAI guardrails only see the task's final output, not the intermediate tool result, so the check is against "is this a real feature at all" rather than "was this specifically in this call's top-N"; catching an invented signal is the main goal, not ranking fidelity.

**`policy_version` (Q35):** carried on every `Verdict` so a past decision stays auditable against the exact policy text it was evaluated under, even after `docs/refund_policy.md` is later revised.

### Data privacy / PII boundary

**No customer-identifiable information reaches any LLM, under any circumstances (Q27).** "Identifiable" covers name, email, phone, physical/shipping address, payment method details, and even the customer ID/email used for login (Q15) — not just the obvious fields.

- **Opaque references, not raw identifiers.** At intake, the Orchestrator resolves the customer's real ID/email to a `customer_ref` (and each claim to an `order_ref`/`claim_ref`) via non-LLM application code. Every MCP tool call, conversation-state key, and prompt an agent's LLM ever sees uses that reference — never the raw string.
- **Tools return de-identified or derived data, not pass-throughs.** `get_account_info` returns `account_age_days`/`prior_claim_count`, not a name or email. `get_tracking_status` compares the claimed and actual delivery address **inside the tool** and returns only `address_match: bool` — neither address string leaves the tool. `issue_refund` resolves the real payment method internally from `order_ref`; the Orchestrator's LLM never sees or supplies it.
- **Photo redaction is mandatory for both vision models.** `redact_photo` auto-blurs incidental text/faces (e.g. a shipping label caught in frame) before a photo reaches GPT-4.1 mini *or* Llama 3.2 Vision — the local/hosted distinction doesn't matter for this rule.
- **The mapping itself lives only in RDS/DynamoDB**, resolved only by non-LLM code: the tool implementations, and the Reviewer Dashboard's backend.
- **Human-facing views are exempt.** The Reviewer Dashboard shows a real human reviewer the actual customer/order details needed to decide — the boundary sits between MCP tool output and *agent LLM context*, not between the system and every human. Since this is the one place raw PII is shown by design, it's the one place that needs a real access gate (Q31): a shared reviewer password, checked before the page renders anything.
- **The boundary extends to Langfuse (Q30).** Traced prompts/tool-calls/verdicts are already de-identified since Langfuse observes what's downstream of the redaction boundary above — but Langfuse adds two fields of its own that aren't covered automatically: its `user_id`/`session_id` grouping fields must be set to `customer_ref`/`claim_ref`, never the raw customer ID/email, and no trace may attach a raw (pre-`redact_photo`) photo upload — only the redacted image or no image at all.

### ML Fraud Scoring model

- **Training data:** Kaggle's **E-Commerce Return Abuse Detection Dataset** (60K synthetic return transactions, labeled Legitimate/Fraudulent Return/Wardrobing — closest public fit to the problem's signals).
- **Approach:** train and evaluate **5 candidate models** — Logistic Regression, Random Forest, XGBoost, LightGBM, CatBoost — on the same train/test split, compare on precision/recall/F1/ROC-AUC (weighted for the ~10-20% fraud-class imbalance).
- **Tracking &amp; selection (Q29):** every candidate's params, metrics, and fitted model are logged as an **MLflow** run under one experiment (e.g. `fraud-risk-scoring`). The best run is picked by sorting on the tracked metrics via `mlflow.search_runs()` (or the MLflow UI) — a repeatable, inspectable process rather than an ad hoc notebook comparison. The winner is promoted through the **MLflow Model Registry** (`Staging` → `Production`), which doubles as the fixed reference point Q3's still-open "numeric floor" decision can be checked against later, without having to re-run all 5 candidates from scratch.
- **Deployment:** the winning model is loaded from the MLflow Model Registry and wrapped as the `score_fraud_risk` MCP tool the Fraud Scoring Agent calls with engineered features (order history, account age, claim frequency, address-mismatch).
- **Feature attribution (Q34):** `score_fraud_risk` also returns the top contributing features for that specific prediction — via SHAP against the registered model, or its native `feature_importances_`/coefficients as a simpler fallback if SHAP proves too slow for a CPU-only tool call. This is what grounds `FraudAssessment.key_signals` in the actual model rather than the agent's own guess.
- **Calibration (Q36, method resolved by Q43):** raw `predict_proba` from tree-ensemble candidates (Random Forest, XGBoost, LightGBM, CatBoost) is a known source of miscalibrated scores — pushed toward the extremes more than the true probability warrants — which matters here because the decision matrix buckets the score into low/medium/high via fixed thresholds. Before registering the winning model, **both isotonic and sigmoid calibration are fit** (`sklearn.calibration.CalibratedClassifierCV`, each on the same held-out calibration split) and compared on calibration quality (e.g. reliability diagram or Brier score); whichever calibrates better is what actually gets logged to MLflow and loaded by `score_fraud_risk` — never the raw uncalibrated classifier.
- **Risk-band source (Q42/Q53 superseded by Q58):** Q42/Q53's cutoff-threshold approach (bucketing a single continuous score at 0.4/0.85) assumed a model shape Slice 2 didn't actually build. The real model predicts `fraud_risk_label` (low/medium/high) as a **direct 3-class target**, not a continuous score to threshold — `FraudAttributor.score()` already uses this: `risk_band` is the model's own argmax class prediction, `risk_score` is its calibrated confidence in that predicted class. No composite score, no arbitrary cutoffs on top of a model that already gives a direct answer.

### Refund policy (Decision Agent's compliance reference)

No suitable public dataset existed for this, so it was drafted and approved during the interview:
- **Return window:** 30 days from delivery (14 days for Change-of-Mind, store credit only, no photo required)
- **Categories:** Damaged in Transit, Wrong Item, Not as Described, Defective/DOA (all photo-required) + Change of Mind
- **Decision matrix** (Image consistency × Fraud risk band): Consistent+Low/Medium → auto-approve; Consistent+High or Partially-consistent+Medium/High → escalate; Partially-consistent+Low → auto-approve; Inconsistent+Low → escalate; Inconsistent+Medium/High → auto-deny
- **Guardrail:** any claim over $200 always escalates regardless of the matrix

Full text is authored as a standalone policy document (`docs/refund_policy.md`), **also committed to git (Q56)** — see "Audit trail" below. **Retrieval is RAG-based (Q50), superseding the earlier S3-direct-fetch approach (Q40) and now `get_refund_policy` entirely (Q56: confirmed full replacement, no full-text tool kept):** the document is chunked **by clause/category (Q56)** — one chunk per claim category, one for the decision matrix, one for the guardrail, following the document's actual structure rather than a fixed token window — and embedded via OpenAI `text-embedding-3-small` into **OpenSearch Serverless** (Q54, revised from Chroma); the Decision MCP server's `search_refund_policy(query)` tool retrieves the **top-5 (Q56)** chunks relevant to the current claim, instead of loading the whole document. **Not gated by the Q55 bearer-token middleware (Q56):** it's read-only, returns no PII, and moves no money — only `issue_refund` is restricted to the Orchestrator's token.

**No-confident-match fallback (Q56):** if `search_refund_policy` comes back with no chunk confidently relevant to the claim, the Decision Agent escalates to human review rather than reasoning from a weak match — treated the same as any other case the policy doesn't clearly cover.

**Versioning (Q35, format resolved by Q46):** the document carries a **semantic version identifier** (e.g. `v1.2` — a header line in the document); each chunk stored in OpenSearch Serverless carries that version as metadata, `search_refund_policy` returns it alongside the retrieved text, and every `Verdict` records it in `policy_version` — so a verdict made today stays auditable against exactly the policy text active when it was made. Minor wording clarifications bump the minor number; changes to the decision matrix, categories, or guardrail bump the major number — a major bump means the document is re-chunked and re-embedded, since old chunks no longer reflect current policy.

**Re-indexing on a major bump (Q56):** old chunks are **deleted** from OpenSearch Serverless — only the current version is ever queryable via `search_refund_policy`, so there's no risk of retrieving a stale rule. **Audit trail:** since OpenSearch itself can no longer answer "what did policy vX say" after a purge, `docs/refund_policy.md` is committed to git specifically so every past version's exact text stays recoverable via `git log`/tags — matching how the rest of this project already preserves history (this document's own interview log) rather than standing up separate versioning infrastructure (e.g. S3 object versioning) for the same purpose.

### Testing & resilience

- **Unit tests** for individual components: MCP tool handlers, the fraud model wrapper, agent logic.
- **Eval harness** running the Decision Agent against known scenarios (clearly fraudulent / clearly legitimate / ambiguous-should-escalate) to sanity-check verdict quality.
- **External API calls** (DummyJSON/FakeStoreAPI/TrackingMore) retry with backoff and surface a clear error to the UI on failure rather than crashing silently.
- **Agent-call timeout + fallback (Q37):** each `Crew(...).kickoff()` call in the Flow is wrapped in a timeout (e.g. `asyncio.wait_for`), not just a try/except — a hang under CPU-only local-inference load needs to be caught the same way a crash is. If Image Parsing or Fraud Scoring fails *or* times out, the claim auto-escalates to human review rather than the Orchestrator waiting indefinitely or the request erroring out with no fallback. This shares a single combined retry ceiling with the Layer-3 guardrail retries from Q28 (one guardrail retry, then the hard timeout, then escalate) so the two retry mechanisms can't compound into an unbounded stall. **The actual timeout value is not yet set (Q49)** — it's tied to a real throughput benchmark against the target hardware (per the CPU-only ~2–5 tok/s risk) rather than a guessed number; `AGENT_CALL_TIMEOUT_S = 180` in the build guide is still only a placeholder until that benchmark runs.
- **Claim-submission rate limiting (Q39, number confirmed by Q45):** FastAPI middleware (e.g. `slowapi`) limits claim submissions to **3 per `customer_ref` per hour** on the submission route — cheap protection against a retry-loop bug or scripted abuse repeatedly hitting the paid GPT-4.1 mini and TrackingMore calls.

64. **Q (surfaced while wiring the Fraud Scoring Agent): `score_fraud_risk(features: dict)` reliably failed through real CrewAI tool-calling — the agent sent an empty `features` dict on every one of 15 real attempts across 3 separate test runs, including one with a literal example JSON object spelled out in the task prompt. 65. **Q (surfaced while wiring the Decision Agent): the approve/deny/escalate decision is a deterministic lookup (Image verdict × Fraud risk band, plus the $200-always-escalate override) — not something that actually needs LLM judgment. Where should this live?**

Matches the same reasoning that made `score_fraud_risk` and `analyze_image` real tools instead of trusted LLM judgment: the rubric requires every business decision to route through MCP, and grounding the decision label in a real, independently-testable tool (verified for real: all 9 real matrix cells plus the $200-override case plus the rejected-`no_photo` case, 11/11 passing) means the Decision Agent's actual contribution is retrieving and citing real policy text, not re-deriving a lookup table an 8B local model could get wrong.
