MULTI-AGENT FRAUD TRIAGE SYSTEM — GUARDRAILS, DECISION MATRIX, TEST RESULTS
================================================================================

SECTION 1: GUARDRAILS
--------------------------------------------------------------------------------
3-layer design: (1) constrained decoding, (2) Pydantic schema, (3) a
guardrail function re-checking the agent's output against the REAL tool
result — catches fabrication a schema alone can't.

Per-agent (Layer 3):
  Orchestrator    intake_guardrail        Missing field -> must ask a
                                           follow-up. order_ref/days_to_return
                                           are no longer agent-handled at all.
  Image Parsing   consistency_guardrail   verdict must match analyze_claim_
                                           photo's real result exactly.
  Fraud Scoring   fraud_assessment_       key_signals must be real model
                  guardrail               feature names, not invented.
  Decision        verdict_guardrail       decision must match apply_decision_
                                           matrix's real result exactly.

Security / business gates:
  IssueRefundGate      issue_refund only accepts the Orchestrator's own
                       bearer token — every other agent is rejected.
  PII boundary         Raw customer identifiers never reach any LLM;
                       resolved to opaque customer_ref first.
  Order ownership      order_ref must be one of the customer's own real,
                       seeded orders — checked against Postgres.
  Reviewer password    All admin endpoints require the shared password,
                       checked server-side.
  Rate limiting        Max 3 new claims / customer / hour.

SECTION 2: DECISION MATRIX
--------------------------------------------------------------------------------
apply_decision_matrix — deterministic, not an LLM judgment call.

Step 1: refund_amount_usd > $200  ->  ESCALATE  (always, overrides below)

Step 2: else, lookup (image_verdict, fraud_risk_band):

  image_verdict \ risk     low        medium      high
  ----------------------------------------------------
  consistent               approve    approve     escalate
  partially_consistent     approve    escalate    escalate
  inconsistent             escalate   deny        deny

SECTION 3: EVALUATION RESULTS
--------------------------------------------------------------------------------
Tool routing accuracy      5 / 5 scenarios     100%
Tool call sequence         5 / 5 scenarios     100%
  (search_refund_policy always called before apply_decision_matrix)

RAGAS (5-scenario sample, real GPT-4.1 mini judge + text-embedding-3-small):

  Metric                        Score
  ------------------------------------
  Context precision             72.6%
  Context recall                100.0%
  Groundedness / faithfulness   70.0%
  Answer relevancy              40.6%

  Retrieval pipeline: hybrid search (k-NN + BM25 merged by Reciprocal Rank
  Fusion) against the real OpenSearch Serverless index, top_k raised from
  5 to 10, then reranked by a real cross-encoder
  (cross-encoder/ms-marco-MiniLM-L-6-v2) -- confirmed working for real:
  the guardrail chunk (the one that literally contains "$200") scores
  dramatically above every other candidate for a "$200" query.

  Context recall reached 100% -- every claim in each reference answer is
  now supported by a retrieved chunk. Raising top_k to 10 was the real
  fix: at top_k=5, reference answers needing multiple distinct policy
  clauses per scenario often didn't get all of them retrieved; at top_k=10
  they do. Context precision fell from its top_k=5 level (94% to 72.6%) as
  the real, expected tradeoff -- a wider candidate set includes some
  less-relevant chunks alongside the ones that closed the recall gap.

  Groundedness/faithfulness rose to 70% (scored against a widened context:
  the real retrieved chunks plus the claim's own given facts -- image
  verdict, fraud risk band, refund amount -- since the Decision Agent's
  reasoning legitimately cites those too, not only policy text). Answer
  relevancy stayed roughly flat at 40.6%, the one metric this retrieval
  work was never targeting.

ML fraud model — calibration comparison (Brier score, lower is better):
  Uncalibrated                0.2409   <- winner by recall, DEPLOYED (rolled back)
  Isotonic calibration        0.2374
  Sigmoid calibration         0.2334   <- best Brier score, but NOT deployed (see finding)

ML fraud model — real precision/recall/F1, computed on the actual test
split against each real model (this was the flagged gap — Brier score was
the only metric ever logged for calibration; these are new, computed just
now, not previously documented anywhere):

  Model                    Precision(w)  Recall(w)  F1(w)   Recall(macro)  High-risk recall
  --------------------------------------------------------------------------------------------
  Uncalibrated (v10) -- DEPLOYED  0.849    0.829     0.835      0.808           0.81
  Isotonic (reconstructed)        0.833    0.839     0.831      0.664           0.30
  Sigmoid (v13, rolled back)      0.824    0.837     0.821      0.611           0.13

  Per-band (low/medium/high) precision, recall, F1 — ALL THREE real model
  variants, same real test set (n=2000: 1196 low, 697 medium, 107 high):

  UNCALIBRATED (v10) -- DEPLOYED
    Risk band     Precision   Recall   F1-score   Support
    -------------------------------------------------------
    low             0.93       0.89      0.91      1196
    medium          0.77       0.72      0.74       697
    high            0.43       0.81      0.56       107
    -------------------------------------------------------
    accuracy                             0.83      2000
    macro avg       0.71       0.81      0.74      2000
    weighted avg    0.85       0.83      0.83      2000



  Reading across the "high" row is the whole finding: recall drops
  0.81 -> 0.30 -> 0.13 as calibration is added (precision rises instead --
  calibration made the model choosier about calling something high-risk,
  which is exactly backwards for a fraud-triage system's actual priority).
  "low" and "medium" bands stay roughly stable across all three -- the
  damage is concentrated entirely in the rare, highest-stakes class.

  Note the real tradeoff visible here: "high" risk precision is low (0.43
  — more false alarms) but recall is high (0.81 — catches most real
  high-risk fraud). For a fraud-triage system, missing real fraud
  (low recall) is the costlier failure mode than over-flagging (low
  precision, which just means more claims get escalated to a human
  reviewer instead of auto-approved) — this is the real, substantive
  reason the uncalibrated model was the right rollback choice, not just
  "it has a better single number."

SECTION 6: DATABASES & APIs
--------------------------------------------------------------------------------
PostgreSQL (RDS fraud-triage-db-pooja, db fraud_triage) -- 7 tables:

  customers            The ONLY table holding a raw customer identifier
                        (email) -- maps it to an opaque customer_ref.
                        Nothing else ever reads the raw identifier back
                        into an LLM's context.
  order_metadata        Synthetic order_date per order_ref (DummyJSON
                        carts have no real purchase date) -- bootstrap-
                        seeded once, then stable.
  customer_orders       Which real DummyJSON orders a customer_ref "owns"
                        (3 per customer, seeded once) -- the chat
                        frontend's order dropdown reads from here.
  customer_profiles     Synthetic account-level fraud features (lifetime
                        orders/returns, dispute count, address match,
                        account age) -- seeded from a real row of the
                        fraud training dataset.
  claims                Complete log of every claim ClaimTriageFlow
                        finishes -- category, description, refund amount,
                        image verdict, risk band, decision, outcome.
                        Upserted per claim_ref.
  review_queue          Only outcome='escalate' claims -- what the Admin
                        reviewer dashboard lists, plus customer_notified_at
                        (set once the customer's been shown the decision).
  refund_transactions   Real issued-refund records -- amount, reason,
                        transaction ID, keyed by (order_ref, claim_ref).

DynamoDB (2 tables):
  conversation-state-dev   Multi-turn chat state.
  claim-frequency-dev      Rate-limiting counters (max 3 claims/customer/hr).

S3 (2 buckets):
  claim-photos-dev      Uploaded claim photos.
  chat-transcripts-dev  Chat transcripts.

OpenSearch Serverless (refund-policy-dev collection):
  Chunked + embedded docs/refund_policy.md -- what search_refund_policy's
  hybrid retrieval queries.

Secrets Manager (5 secrets): AWS creds, Azure OpenAI keys, 4 per-agent MCP
bearer tokens, Langfuse keys, and app config (DATABASE_URL,
REVIEWER_PASSWORD, table/bucket names, BACKEND_URL, MCP_SERVER_HOST/PORT).

Backend REST API (FastAPI, backend/main.py):
  GET  /health
  POST /claims
  POST /messages                (+ /messages/photo)
  POST /orders
  POST /claim-updates           customer polling for reviewer decisions
  GET  /tool-registry           reviewer-only
  GET  /claims                  reviewer-only, full claim log
  GET  /review-queue            reviewer-only
  POST /review-queue/{claim_ref}/decide   reviewer-only
  POST /documents                reviewer-only, RAG doc ingest

MCP tool server (mcp-servers/orchestrator_server.py, FastMCP) -- one shared
server, 4 per-agent token-scoped tool sets:
  Orchestrator     resolve_customer_ref, get_order, list_customer_orders,
                   get_days_to_return, issue_refund (the only money-moving
                   tool), get/put_conversation_state, store/get_photo,
                   store_transcript
  Image Parsing    analyze_claim_photo
  Fraud Scoring    get_order, get_account_info, get_claim_frequency,
                   increment_claim_frequency, get_tracking_status,
                   score_fraud_risk
  Decision         search_refund_policy, apply_decision_matrix

External APIs: DummyJSON (fake order/product data), Azure OpenAI (GPT-4.1
mini for all agents + embeddings for RAG), TrackingMore (shipment
tracking, optional), Langfuse (observability).
